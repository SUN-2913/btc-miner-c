## Общая картина

Клиент Stratum v1: получает от пула шаблоны блоков, собирает заголовки и ищет
nonce, при котором двойной SHA-256 оказывается меньше target.

Программа намеренно разделена на две очень разные половины:

| Половина | Как часто исполняется | Влияние на скорость | Чем написана |
|---|---|---|---|
| Протокол, сборка задания, интерфейс | раз в сообщение / раз в задание | нулевое | обычный C |
| Хеширование | миллиарды раз в секунду |决定 всё | asm / AVX2 / C |

Все усилия по оптимизации относятся ко второй половине. Первая написана ради
ясности, а не скорости: наивный JSON-парсер и учебный SHA-256 там уместны,
потому что выполняются раз в задание, а не раз в nonce.

## Модель потоков

```
                    +------------------------------+
                    |        главный поток         |
                    |  recv() от пула              |
                    |  разбор JSON                 |
                    |  обновление Shared под мьютексом |
                    |  разгребание очереди событий |
                    |  печать статуса и событий    |
                    +------------------------------+
                        ^                    |
        очередь событий |                    |  Shared { job, target, best }
        (g_ev_mtx)      |                    v  (g_state_mtx)
        +-----------+-----------+-----------+-----------+
        | worker 0  | worker 1  | worker 2  | worker N-1|
        | хеширует  | хеширует  | хеширует  | хеширует  |
        +-----------+-----------+-----------+-----------+
                        |
                        |  mining.submit  (g_send_mtx)
                        v
                       пул
```

**Печатает только главный поток.** Строка статуса перерисовывается на месте
через `\r`; два одновременно печатающих потока порвали бы её в клочья. Воркеры
вместо печати кладут текст в очередь.

**Воркеры пишут в сокет напрямую.** TCP полнодуплексный, поэтому отправка шары
из воркера параллельно с чтением в main безопасна; мьютекс сериализует записи
и защищает дескриптор сокета при переподключениях.

**Потоки бенчмарка** существуют только во время тюнинга при старте и
присоединяются (join) до начала майнинга.

| Мьютекс | Что защищает | Как долго удерживается |
|---|---|---|
| `g_state_mtx` | `Shared`: задание, target, extranonce1, best | копирование структуры, раз в батч |
| `g_send_mtx` | `g_sock` и записи в сокет | один `send()` |
| `g_ev_mtx` | список событий воркер → main | перестановка указателей |

## Последовательность запуска

```
main()
 |-- разбор CLI; -a и -p обязательны (встроенных значений нет)
 |-- печать модели CPU и его возможностей
 |-- [-d MIN] цикл ожидания, CPU полностью простаивает
 |-- выбор движка
 |     |-- задан -e shani|avx2|scalar -> берём его, без замеров
 |     +-- auto -> замер каждого доступного движка на N потоках, берём быстрый
 |-- selftest по эталонным векторам --(несовпадение)--> exit(2)
 |-- запуск N воркеров
 +-- цикл переподключения:
       connect -> subscribe -> authorize -> цикл чтения -> при сбое пауза 5 с
```

Задержка стоит **до** тюнинга намеренно. При автозапуске вместе с Windows первая
минута забита стартовой нагрузкой; замер в этот момент дал бы искажённый
рейтинг. Во время задержки процесс только спит.

## Путь данных от JSON к хешу

`mining.notify` **не** содержит готовый заголовок. В нём лежат части для сборки,
разрезанные вокруг extranonce — чтобы каждый майнер мог менять своё пространство
поиска, не спрашивая пул.

```
mining.notify
   |
   v
Job { job_id, prevhash, coinb1, coinb2, branches[], version, nbits, ntime }
   |
   |  раз в extranonce2 (то есть раз в ~4 млрд хешей или при новом задании)
   v
coinbase = coinb1 || extranonce1 || extranonce2 || coinb2
   |
   v
mr = SHA256d(coinbase)
для каждой ветки b:   mr = SHA256d(mr || b)          <- свёртка Меркла
   |
   v
header[80] = version || prevhash || mr || ntime || nbits || nonce
   |
   |-- header[0..63]  --> midstate()      (считается один раз)
   +-- header[64..79] --> tail[16]
                            |
                            |  на каждый nonce  <- ГОРЯЧИЙ ЦИКЛ
                            v
                  sha256d_tail(mid, tail) --> 32-байтный хеш
                            |
                            |-- хеш <= target шары   -> mining.submit
                            +-- хеш <= target сети   -> НАЙДЕН БЛОК
```

Важные детали:

- `extranonce1` пул выдаёт **на каждое соединение**. Две машины с одинаковым
  именем воркера всё равно ищут в непересекающихся пространствах.
- Ветки Меркла приходят во внутреннем порядке байтов и конкатенируются как есть.
- Пустой список веток означает, что в блоке только coinbase; корнем Меркла тогда
  является сам txid coinbase. Цикл свёртки просто не выполнится ни разу.

## Заголовок блока и разделение midstate

| Смещение | Размер | Поле | Порядок байтов в заголовке |
|---:|---:|---|---|
| 0 | 4 | version | little |
| 4 | 32 | prev_block_hash | внутренний (little) |
| 36 | 32 | merkle_root | внутренний (little) |
| 68 | 4 | ntime | little |
| 72 | 4 | nbits | little |
| 76 | 4 | nonce | little |

SHA-256 поглощает блоки по 64 байта. Заголовку в 80 байт нужны два блока, причём
второй почти целиком состоит из паддинга. Nonce живёт именно во втором блоке:

```
блок 1: header[0..63]     version + prevhash + первые 28 байт merkle
блок 2: header[64..79]    хвост merkle + ntime + nbits + NONCE, затем паддинг
блок 3: 32-байтный первый дайджест, затем паддинг   <- второй SHA-256
```

Блок 1 от nonce не зависит. Посчитать его один раз и продолжить с полученного
состояния — это и есть оптимизация **midstate**:

```
наивно:    C1 + C2 + C3   на каждый nonce   (3 сжатия)
midstate:  C1 один раз, дальше C2 + C3      (2 сжатия)  -> ~1.5x
```

`midstate()` сохраняет восемь слов состояния как нативные little-endian dword —
не как печатный дайджест. Именно такую раскладку ожидает `sha256d_tail`, когда
возобновляет счёт.

## Горячий цикл

```c
for (;;) {
    if (shared.epoch != my_epoch)      /* новое задание / сложность / extranonce1 */
        перечитать всё, начать скан заново;

    if (!have_prefix)                  /* раз в extranonce2 */
        собрать coinbase -> merkle -> header -> midstate + tail;

    for (65536 хешей) {
        вписать nonce в tail[12..15];
        hash = engine(midstate, tail);
        обновить best;
        if (hash <= share_target)   отправить шару;
        if (hash <= network_target) сообщить о блоке;
        nonce++;
        if (nonce переполнился) { extranonce2 += nthreads; пересобрать префикс; }
    }
    опубликовать счётчики; влить best;
}
```

**Разделение пространства поиска.** Воркер `t` берёт `extranonce2 = t, t+N, t+2N, …`
и для каждого прогоняет весь 32-битный диапазон nonce. Никакой координации,
никаких пересечений.

**Механизм epoch.** Main увеличивает `Shared.epoch` при каждом notify, смене
сложности или ответе на subscribe. Воркеры сравнивают его со своей копией на
границах батчей. Так новый блок в сети доходит до всех воркеров за один батч —
миллисекунды — без всяких условных переменных.

**Почему батч именно 65536.** Он размазывает стоимость мьютекса и атомарного
счётчика по достаточному объёму работы, чтобы они были бесплатны, и при этом
держит задержку переключения задания намного ниже интервала заданий пула.
В AVX2-пути батч — 8192 вызова × 8 lanes = те же 65536.

**Фильтр best difficulty.** Собирать полный `u256` для каждого хеша расточительно,
поэтому сначала сравнивается старшее слово; полное сравнение happens только
когда хеш теоретически может побить рекорд.

## Движки хеширования

| Движок | Требует | Сжатий на nonce | Хешей за вызов |
|---|---|---:|---:|
| `scalar` | любой x86-64 | 2 | 1 |
| `shani` | SHA-NI + SSSE3 + SSE4.1 | 2 | 1 |
| `avx2` | AVX2 | 2 | 8 |

Все три используют midstate. Движок выбирается один раз при старте и кладётся в
указатель на функцию, поэтому горячий цикл платит только за косвенный вызов.

### AVX2 multi-buffer

Один SHA-256 — длинная последовательная цепочка зависимостей; исполнительные
порты частично простаивают. Nonce независимы, поэтому восемь хешей считаются
бок о бок, по одному в каждом 32-битном lane регистра YMM:

```
          lane0   lane1   lane2   ...   lane7
W[3]  =   n+0     n+1     n+2     ...   n+7     <- единственное различающееся слово
W[i]  =   константа, размноженная по всем lanes, для i != 3
st[j] =   восемь копий слова состояния j, эволюционирующих параллельно
итог:     восемь дайджестов за проход
```

Удобная деталь второй фазы: байты первого дайджеста — это и есть слова состояния
в big-endian, поэтому второе сообщение получается как `W[i] = st[i]`, вообще без
перекладываний.

### Почему тюнинг идёт на N потоках

Потому что победитель меняется с числом потоков. Замеры на реальном железе:

| CPU | Движок | 8 потоков | 16 потоков | 24 потока |
|---|---|---:|---:|---:|
| i7-10700F (без SHA-NI) | scalar | 11.0 | – | – |
| i7-10700F | avx2 | 70.4 | 91.4 | – |
| i9-12900KF | shani | 85.6 | 142.0 | 202.9 |
| i9-12900KF | avx2 | 102.2 | 136.6 | 169.6 |

(MH/s.) Кроссоверы объясняют три эффекта:

1. **SHA-NI упирается в латентность**, поэтому SMT заполняет простои: примерно +66%.
2. **AVX2 уже насытил векторные порты**, поэтому SMT добавляет лишь ~34%.
3. **Гибридные E-ядра** исполняют 256-битные операции в два прохода, но SHA-NI у
   них нативный — на полном числе потоков рейтинг снова переворачивается.

Однопоточный микробенчмарк выбрал бы неверный движок. Поэтому замер поднимает
ровно `-t N` потоков и гоняет ту же внутреннюю работу, что и майнинг
(хеш + фильтр best + сравнение с target), а не одно только ядро хеша.

## Target сложность и порядок байтов

Хеш трактуется как 256-битное little-endian число, хранится в четырёх 64-битных
словах (`l[0]` — младшее). Сырые байты дайджеста уже лежат в этом порядке.

```
DIFF1  = 0xffff * 2^208                  (target «сложности 1»)
target = DIFF1 / difficulty
```

В игре два разных target:

| Target | Откуда | Смысл |
|---|---|---|
| target шары | `mining.set_difficulty` | лёгкий; proof of work для статистики пула |
| target сети | `nbits` из задания | тяжёлый; настоящий блок |

Сетевой target всегда строже, поэтому проверка блока выполняется только внутри
срабатывания шары — одно сравнение экономится на каждом обычном хеше.

### Правила порядка байтов (классический источник багов)

| Что | Правило |
|---|---|
| `version`, `nbits`, `ntime` из Stratum | big-endian hex → в заголовок пишем little-endian |
| `prevhash` из Stratum | байты развёрнуты **внутри каждого 4-байтного слова**; разворачиваем пословно, а не целиком |
| ветки Меркла | внутренний порядок, конкатенируем как есть |
| половины coinbase | сырые байты, без преобразований |
| слова сообщения SHA-256 | big-endian; длина в паддинге — big-endian 64-битное число бит |
| `nonce` в `mining.submit` | big-endian hex числового значения |
| `extranonce2` в `mining.submit` | hex ровно тех байтов, что были вставлены |
| дайджест для показа | обратный порядок байтов |

## Обмен по Stratum

```
майнер                                    пул
  |  mining.subscribe   (id 1)              |
  | --------------------------------------> |
  |     [subscriptions, extranonce1, size]  |
  | <-------------------------------------- |
  |  mining.authorize   (id 2)              |
  | --------------------------------------> |
  |                             true/false  |
  | <-------------------------------------- |
  |                mining.set_difficulty    |
  | <-------------------------------------- |
  |                       mining.notify     |
  | <-------------------------------------- |
  |  mining.submit      (id 100, 101, ...)  |
  | --------------------------------------> |
  |                             true/false  |
  | <-------------------------------------- |
```

Идентификаторы ответов: `1` — subscribe, `2` — authorize, `>= 100` — вердикт по
шаре. Всё остальное — уведомления сервера, разбираются по имени метода.

Сообщения — JSON, разделённый переводами строк. Буфер приёма держит неполную
строку, пока не придёт остаток; таймаут сокета 200 мс позволяет главному циклу
просыпаться и перерисовывать статус, даже когда пул молчит.

## Правила многопоточности

- `Shared` читается и пишется только под `g_state_mtx`. Воркеры копируют задание
  целиком по значению раз в смену epoch, дальше работают со своей копией.
- Буферы фиксированного размера внутри `Job` означают **отсутствие аллокаций в
  горячем цикле**.
- Счётчики — `_Atomic uint64_t`, накапливаются локально и публикуются раз в батч,
  а не инкрементируются на каждом хеше.
- `best` ведётся каждым воркером отдельно и вливается под мьютексом; общее
  значение только уменьшается (меньший хеш — лучший).
- JSON-парсер использует курсор уровня файла и вызывается только из main.
- Каждое разобранное дерево освобождается через `jfree()`; долгоживущий майнер
  не течёт.

## Проверка корректности

`selftest()` выполняется до любого майнинга и проверяет:

1. Два жёстко заданных эталонных дайджеста SHA-256d, полученных независимой
   реализацией, против software-пути.
2. Путь midstate против тех же векторов.
3. Ассемблерный путь, если выбран SHA-NI.
4. Путь AVX2 на трёх базах nonce, включая `0xFFFFFFF8` — последнюю полную группу
   перед переполнением 32-битного nonce, чтобы поймать арифметику lanes на краю.

Сравнивать быстрые пути только с собственным software-кодом недостаточно: общая
ошибка сократилась бы сама с собой. Внешние векторы закрывают эту дыру. При
несовпадении программа завершается, а не начинает отправлять невалидные шары.

## Обработка сбоев

| Событие | Поведение |
|---|---|
| connect не удался | печать, пауза 5 с, повтор |
| пул закрыл сокет | инвалидировать задание, переподключиться |
| таймаут приёма | норма; перерисовать статус и продолжить |
| новое задание / сложность | увеличить epoch; воркеры перезапускают скан |
| шара отклонена | посчитать, напечатать; обычно это stale |
| self-test не совпал | exit(2), майнинг не начинается |

При переподключении сессия инвалидируется (`have_job = 0`, `extranonce1`
очищается), воркеры простаивают до свежих subscribe и notify. Шары, queued для
старой сессии, не переотправляются — их job id больше не существуют.

## С чего начинать чтение

1. `main()` — последовательность запуска и цикл переподключения.
2. `worker()` — горячий цикл; всё остальное существует, чтобы его кормить.
3. `parse_job()` + `handle_line()` — как сообщения пула становятся состоянием.
4. `midstate()` и `sha256d_tail_sw()` — оптимизация, написанная читаемым C.
5. `sha256d_tail_x8()` — то же самое, но в восемь lanes.
6. `sha256ni.S` — сначала прочитайте шапку файла: соглашения по регистрам и
   неявный операнд `XMM0` объяснены там.

## Ограничения и идеи

Известные пробелы, все оставлены намеренно ради ясности:

- Только Stratum v1; нет TLS, version rolling (`mining.configure`),
  `mining.set_extranonce`, роллинга `ntime`.
- SHA-NI-ассемблер использует **двухпроходное** расписание сообщений: пишет
  `W+K` в стек и читает обратно. Слитное однопроходное (Linux kernel, RustCrypto)
  убирает 32 обращения к стеку на блок.
- Скалярный SHA-256 — учебный цикл с полным массивом `W[64]`. Скользящее окно из
  16 слов и развёрнутые раунды сделали бы его конкурентным с тюнингованными
  библиотеками — и тогда преимущество midstate проявилось бы полностью.
- JSON-парсер минимальный и заточен под Stratum, это не библиотека общего назначения.

Хорошие упражнения, если хочется именно поучиться на этом коде:

1. Реализовать слитное расписание SHA-NI и замерить разницу.
2. Добавить роллинг `ntime`, чтобы воркер мог обновлять метку времени сам.
3. Оптимизировать скалярное сжатие, затем снова сравнить `-e scalar` и `-e avx2`.
4. На гибридном CPU попробовать выбирать движок **по потокам** (AVX2 на P-ядрах,
   SHA-NI на E-ядрах) и проверить, побьёт ли это единый глобальный выбор.
